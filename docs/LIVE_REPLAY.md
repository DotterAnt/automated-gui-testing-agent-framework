# Persistent step development

The MCP server retains one live desktop plan at a time. Begin defaults to RecordedBatch: explore with Batch, record and Complete before generating the replay. Then Verify executes the saved bodies and retains a failed live session for recovery. agta_replay and agta_explore action Replay reach the same session. Explicit Live mode remains available for saved-body discovery, with read-only Batch. Older manifests retain their mode. `Start` preflights the saved template and loads setup once without running the driver/exit; RecordedBatch requires completed exploration first. One literal body per row; setup cannot dispatch framework GUI calls.

`Step` executes the next row only, with normal command logging, policy, ownership and expected-result assertions. Failure captures evidence and keeps the current application state. `Status` supplies a bounded command diagnostic and acknowledges review. `Repair` performs sequential CLI commands in that same context and stops at the first failure. GUI input requires an explicit `stepIndex` identifying the actual CSV row; each response includes that row and the unchanged `nextStepIndex`. Read-only requests may default to the pending row and do not taint a clean session. Input repairs do. Restore the failed body's entry state before rerunning it; a partially performed body can duplicate actions. For a manually completed pending row, record its own receipts, then `Skip` with an explicit reason to advance. Skip records BYPASSED, never PASS. Never reassign historic receipts to another row. Code/body changes are revalidated before another action.

Variables, CLI scope, ownership and Context.ExecutionEvidenceRoot survive. Saved bodies and top-level helper functions reload in place, including added/removed helpers. Parameter/import/initializer changes require Close/Start. Plan functions are not exported into the MCP server's shared scope. A helper edit after execution taints whole-run qualification without discarding first-attempt successes. Successful retries have RECOVERY_SUCCESS; failures remain in the journal. Prefer repairing the failed action and finishing its row live, then Skip and continue Step; retry a whole body only after restoring entry state. No Close/Start is needed for selector/helper edits.

`Close` performs normal owned cleanup. Review/RecordSteps must already cover every explored row before qualification; Close seals exploration only after those checks. A clean session can be closed again to finish qualification if recording was missing; GUI cleanup is not repeated. If every body passed on its first attempt in order, the final script still contains those bodies, recording/preflight/cleanup pass and no repair intervened, Close writes a normal qualifying result with `executionMode: IncrementalFirstAttempt`. Verify returns that same result for an unchanged qualified revision, without rerunning. A repaired/skipped/partial session writes only diagnostic results and must be followed by a clean Verify from row one.

Diagnostic journals use `results/diagnostic-<executionId>.json`, distinct statuses and `qualifying: false`; they never overwrite `results/result.json`. Normal executions also retain `results/replay-<executionId>.json`, including failed full replays. Logs contain one structured parsed receipt per command, plus row/attempt identity, without a duplicate raw JSON envelope. `agta_inspect` reads bounded structured details and leaves full evidence on disk. These are audit/provenance checks, not a sandbox against independent external desktop activity.

An unfinished failed session rejects plain Close, preserving its app, variables and successful prefix for live recovery. Reach the last row before normal Close. If cancelled or live state is unrecoverable, provide an explicit Close `reason`; owned cleanup still runs and the journal records ABANDONED without inventing passed rows. A real initializer/import/parameter change also permits cleanup because live setup cannot be reloaded safely. Helper/selector edits are recoverable in place.

Incremental qualification records `timing.activeExecutionMs` and `pausedMs`. `totalMs` is elapsed session time, including agent development between steps; do not interpret that pause time as CLI/script execution latency.

`Verify` requires complete reviewed exploration, loads a fresh plan after cleanup and executes saved bodies in order using the same step runtime. If all pass, normal cleanup/qualification completes that attempt without repetition. Under MCP/Auto, after 30 seconds it yields between completed rows with IN_PROGRESS and nextStepIndex. Continue Step in that same live session, then Close after the final row. This preserves first-attempt qualification without a second full run. A failed Verify stops at its failed body, keeps the live application/context, returns diagnostic failure and the successful first-attempt prefix, and blocks another Verify while the session is open. Review Status, repair/retry Step, continue pending bodies, then Close and make one clean Verify. No automatic rollback or repeated successful prefix is performed.

An unqualified Live-mode revision cannot execute standalone. Successful qualification records its exact source hash in the exploration manifest. The unchanged delivered script can then run standalone normally; edits require new live verification. Historical result files remain available. This authoring protocol is not an execution sandbox against arbitrary shell code or deliberate manifest changes.
