# Persistent step development

The MCP server retains one live desktop plan at a time. `Start` parses/preflights the saved template, loads its setup in an isolated module, and defines its literal StepBodies array without evaluating the final driver or exit. Existing template-based scripts are compatible. Scriptblocks must be literal, one per CSV row; setup cannot dispatch framework GUI calls.

`Step` executes the next row only, with normal command logging, policy, ownership and expected-result assertions. Failure captures evidence and keeps the current application state. `Status` supplies a bounded command diagnostic and acknowledges review. `Repair` performs sequential CLI commands in that same context; it stops at the first failure. Read-only requests do not taint an otherwise clean session. Input repairs do. Restore the failed body's entry state before rerunning it; rerunning a partially performed body from the wrong state can duplicate actions. There is no automatic input retry or fabricated rollback. `Skip` requires an explicit reason and records BYPASSED, never PASS. Code/body changes are revalidated before another action.

Variables, CLI scope, ownership, helpers and Context.ExecutionEvidenceRoot survive. Only saved body edits reload; changes to setup require Close/Start. First-attempt successes have `countsAsSuccessfulStep: true`; successful retries have RECOVERY_SUCCESS. Failures remain in the attempt journal. Editing already executed code, failing, repairing with input or skipping taints whole-run qualification. Passing a later row on its first attempt still preserves that fact.

`Close` performs normal owned cleanup. Review/RecordSteps must already cover every explored row before qualification; Close seals exploration only after those checks. A clean session can be closed again to finish qualification if recording was missing; GUI cleanup is not repeated. If every body passed on its first attempt in order, the final script still contains those bodies, recording/preflight/cleanup pass and no repair intervened, Close writes a normal qualifying result with `executionMode: IncrementalFirstAttempt`. Verify returns that same result for an unchanged qualified revision, without rerunning. A repaired/skipped/partial session writes only diagnostic results and must be followed by a clean Verify from row one.

Diagnostic journals use `results/diagnostic-<executionId>.json`, distinct statuses and `qualifying: false`; they never overwrite `results/result.json`. Normal executions also retain `results/replay-<executionId>.json`, including failed full replays. Logs contain one structured parsed receipt per command, plus row/attempt identity, without a duplicate raw JSON envelope. `agta_inspect` reads bounded structured details and leaves full evidence on disk. These are audit/provenance checks, not a sandbox against independent external desktop activity.

Incremental qualification records `timing.activeExecutionMs` and `pausedMs`. `totalMs` is elapsed session time, including agent development between steps; do not interpret that pause time as CLI/script execution latency.

`Verify` loads a fresh plan after cleanup, requires complete exploration and invokes the same standard all-row driver. A modified final body invalidates previous qualification. A failed Verify remains a failed full execution; continue live development and restore state deliberately before another qualifying attempt.
